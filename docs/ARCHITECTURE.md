# Архитектура проекта

`Site Audit` состоит из клиентской части, backend API, базы данных, брокера очередей, набора Celery workers, поискового провайдера и ML-слоя.

## Общая схема

```text
Пользователь
    |
    v
React frontend
    |
    v
FastAPI backend
    |
    +--> SQLite
    +--> Redis
    +--> Celery workers
    |       |
    |       +--> загрузка страниц
    |       +--> анализ snapshot
    |       +--> семантический анализ
    |       +--> ML scoring
    |       +--> рекомендации
    |
    +--> SearXNG
    |
    +--> CatBoost model artifact
```

## Frontend

Frontend находится в `frontend/` и реализован на `React + TypeScript + Vite`.

Он отвечает за:

- форму запуска аудита;
- отображение текущего состояния;
- историю аудитов;
- обзор результата;
- сравнение конкурентов;
- список рекомендаций;
- таймлайн выполнения;
- страницу состояния runtime;
- экспорт отчёта.

Frontend не рассчитывает score самостоятельно. Он получает данные от backend API и отображает их в пользовательском интерфейсе.

## Backend API

Backend находится в `backend/` и реализован на `FastAPI`.

Основные обязанности backend:

- принимать запрос на запуск аудита;
- валидировать входные данные;
- создавать запись аудита;
- ставить задачи в Celery;
- хранить события и результаты;
- отдавать данные для интерфейса;
- выполнять расчёт признаков и score;
- формировать рекомендации.

## База данных

В MVP используется SQLite. Она хранит:

- записи аудитов;
- статусы;
- события таймлайна;
- результат аудита;
- данные сравнения;
- рекомендации;
- историю запусков.

SQLite выбрана как простой вариант для дипломного проекта и демонстрационного размещения. При росте нагрузки её можно заменить на PostgreSQL без изменения основной идеи архитектуры.

## Redis и Celery

Redis используется как брокер сообщений и backend результатов для Celery. Celery выполняет вычислительные и сетевые стадии аудита вне HTTP-запроса.

Это позволяет:

- не держать долгий аудит внутри одного запроса браузера;
- параллельно обрабатывать страницы конкурентов;
- разделять сетевые, семантические и ML-задачи;
- отслеживать состояние очередей;
- масштабировать отдельные типы workers.

## Worker-профили

В проекте используется несколько профилей workers:

| Профиль | Назначение |
| --- | --- |
| `pipeline` | orchestration, admission control и постановка стадий |
| `network` | загрузка целевой страницы, поиск и загрузка конкурентов |
| `heavy_analysis` | тяжёлый анализ snapshot |
| `semantic_cpu` | семантические вычисления |
| `cpu_ml` | извлечение признаков, ML scoring, рекомендации и финализация |

Такое разделение показывает распределённые вычисления на уровне приложения: разные стадии аудита выполняются разными рабочими процессами и очередями.

## SearXNG

SearXNG используется как локальный поисковый провайдер для получения конкурентных страниц. Он запускается через Docker Compose вместе с Redis.

Backend обращается к SearXNG по адресу `http://127.0.0.1:8888`, получает выдачу по запросу пользователя и формирует список конкурентов для анализа.

## ML-модель

Активная модель хранится в:

- `backend/artifacts/page_quality_model.pkl`;
- `backend/artifacts/page_quality_model.metadata.json`.

Во время аудита модель не обучается. Она получает рассчитанные признаки страницы и возвращает оценку. Обучающие датасеты, benchmark-отчёты и исследовательские материалы не нужны для обычного запуска приложения и не публикуются в GitHub.

## Поток данных

1. Пользователь запускает аудит во frontend.
2. Frontend отправляет запрос в FastAPI.
3. FastAPI создаёт запись аудита в SQLite.
4. Backend ставит задачу в очередь Celery.
5. Worker загружает целевую страницу и сохраняет snapshot.
6. Другие worker-стадии извлекают признаки.
7. SearXNG возвращает страницы конкурентов.
8. Конкуренты анализируются параллельно.
9. ML-модель рассчитывает первичную оценку страницы.
10. Backend рассчитывает конкурентный score.
11. Recommendation layer формирует рекомендации.
12. Frontend отображает итоговый результат.

## Runtime endpoints

Для диагностики используются служебные endpoints:

- `/health/live` - backend запущен;
- `/health/ready` - стек готов к аудиту;
- `/health/metrics` - состояние очередей и workers;
- `/health/model` - активная ML-модель;
- `/health/model/monitoring` - агрегированная информация по использованию модели.

Эти endpoints помогают понять, готов ли стек к запуску аудита и где находится проблема, если аудит выполняется медленно.
