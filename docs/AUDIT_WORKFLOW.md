# Подробное описание работы SEO-аудита

Этот документ описывает полный путь аудита: от ввода данных пользователем до итогового отчёта с рекомендациями. Описание предназначено для разработчика или проверяющего, который хочет понять внутреннюю логику приложения без чтения всего кода.

## 1. Запуск аудита

Пользователь открывает интерфейс приложения и задаёт два основных параметра:

- URL страницы, которую нужно проверить;
- поисковый запрос, по которому эта страница должна конкурировать.

После отправки формы frontend вызывает backend API. Сервер создаёт запись аудита в базе данных SQLite, фиксирует начальный статус и передаёт выполнение в распределённый pipeline. Пользователь сразу видит, что аудит запущен, а дальнейшие изменения статуса приходят из сохранённых событий и результата аудита.

## 2. Создание задачи и распределённое выполнение

Backend не выполняет весь аудит одним длинным HTTP-запросом. Вместо этого создаётся цепочка задач Celery. Redis используется как брокер сообщений и как backend результатов.

Аудит делится на стадии:

- orchestration и постановка следующих стадий;
- загрузка целевой страницы;
- тяжёлый анализ сохранённого snapshot;
- извлечение признаков;
- семантический анализ;
- ML-оценка;
- получение конкурентов;
- параллельный анализ страниц конкурентов;
- генерация рекомендаций;
- финализация результата.

Такой подход нужен для распределённых вычислений: разные типы работы можно выполнять отдельными worker-профилями. Сетевые задачи не блокируют расчёт признаков, а семантические операции вынесены в отдельную очередь.

## 3. Загрузка целевой страницы

На первом содержательном этапе backend загружает целевую страницу. Система фиксирует:

- исходный URL;
- финальный URL после редиректов;
- HTTP-статус;
- цепочку редиректов;
- HTML-код;
- извлечённый текст;
- основные элементы DOM.

Если страница недоступна, возвращает ошибку, запрещена к индексации или содержит слишком мало полезного текста, аудит не скрывает проблему. В результате отображается причина низкой оценки или невозможности полноценного анализа.

## 4. Snapshot страницы

После загрузки создаётся snapshot - сохранённое представление страницы на момент проверки. Он нужен, чтобы последующие стадии работали с одним и тем же исходным материалом.

Snapshot позволяет:

- не загружать страницу повторно для каждого анализатора;
- воспроизводимо пересчитывать признаки;
- объяснять результат аудита через сохранённые данные;
- анализировать целевую страницу и конкурентов по единой схеме.

В snapshot входят HTML, текст, заголовки, ссылки, кнопки, метатеги, canonical, robots, viewport, язык страницы и другие извлечённые элементы.

## 5. Технические признаки

Технический блок показывает, насколько страница доступна и понятна для поисковой системы. Система анализирует:

- корректность HTTP-ответа;
- количество редиректов;
- наличие и согласованность canonical;
- meta robots и X-Robots-Tag;
- признаки noindex и nofollow;
- наличие viewport;
- указание языка страницы;
- hreflang-ссылки;
- глубину URL;
- количество query-параметров;
- общую техническую готовность страницы.

Эти признаки влияют на оценку, потому что страница может иметь хороший текст, но быть плохо доступной для поискового робота или иметь слабые технические сигналы.

## 6. Текстовые признаки

Текстовый анализ оценивает, есть ли на странице достаточно содержательного материала для раскрытия запроса. Система учитывает:

- объём извлечённого текста;
- структуру заголовков;
- наличие title и meta description;
- соотношение текста и HTML;
- плотность полезного текста;
- наличие списков, ссылок, кнопок и структурных элементов;
- совпадение значимых слов запроса с текстом страницы.

Текстовый блок не сводится к простому подсчёту слов. Большой объём текста сам по себе не гарантирует хорошую оценку: важна связь текста с запросом и конкурентным окружением.

## 7. Коммерческие и trust-признаки

Для коммерческих страниц важны признаки доверия и готовности страницы к продаже или заявке. Система проверяет:

- наличие телефона;
- наличие email;
- наличие адреса;
- часы работы;
- цены и валюты;
- сведения о доставке;
- сведения об оплате;
- гарантии;
- возврат;
- отзывы;
- рейтинг;
- FAQ;
- призывы к действию;
- мессенджеры;
- юридические реквизиты;
- признаки идентификации компании.

Эти признаки особенно важны для посадочных страниц услуг, интернет-магазинов и коммерческих запросов. Если у конкурентов есть сильные коммерческие блоки, а на целевой странице они отсутствуют, система может сформировать рекомендацию по добавлению таких элементов.

## 8. Семантические признаки и проверка запроса

Семантический слой оценивает, соответствует ли страница именно тому запросу, который ввёл пользователь. Это нужно, чтобы страница не получала среднюю оценку только за счёт общих SEO-признаков.

Система выделяет значимые части поискового запроса, сравнивает их с текстом страницы и учитывает смысловую близость. Для русского текста используется provider-based semantic layer; в проекте предусмотрены RoSBERTa/MiniLM-подходы.

Если страница явно не соответствует запросу, аудит может завершиться раньше тяжёлых стадий. В этом случае пользователь видит не техническую ошибку, а понятное состояние: страница не подходит под заданный запрос.

## 9. Получение конкурентов

Для конкурентного анализа система обращается к локальному SearXNG. Поисковый провайдер возвращает страницы из выдачи по тому же запросу.

Дальше backend:

- нормализует URL конкурентов;
- исключает дубли;
- подготавливает список страниц для анализа;
- отправляет страницы конкурентов в параллельные задачи Celery.

Конкуренты нужны не для копирования их содержимого, а для понимания уровня выдачи. Одна и та же страница может выглядеть сильной сама по себе, но быть слабой на фоне top-N конкурентов.

## 10. Анализ конкурентов

Каждая конкурентная страница проходит похожий путь: загрузка, snapshot, извлечение признаков, семантическая проверка и ML-оценка. Эти задачи выполняются через fan-out: несколько конкурентов могут обрабатываться одновременно.

Если часть конкурентов недоступна, заблокирована или содержит слишком мало полезных данных, система не подменяет их вымышленными значениями. Качество конкурентного контекста отражается в результате аудита.

## 11. ML-оценка страницы

ML-слой использует модель CatBoost. На вход модели передаётся набор числовых признаков страницы. В текущем runtime используется активный артефакт:

- `backend/artifacts/page_quality_model.pkl`;
- `backend/artifacts/page_quality_model.metadata.json`.

Модель не обучается во время каждого аудита. Во время аудита она только применяет уже обученный артефакт к новым данным. Это важно: изменение score в процессе аудита связано не с дообучением модели, а с появлением новых данных, прежде всего с обработкой конкурентов и финальным пересчётом конкурентного score.

## 12. Конкурентный score

Первичная ML-оценка показывает качество самой страницы. После анализа конкурентов система рассчитывает конкурентный score. Он учитывает:

- оценку целевой страницы;
- средний уровень обработанных конкурентов;
- сильнейшего конкурента;
- позицию целевой страницы относительно конкурентного окружения;
- качество полученного конкурентного контекста.

Поэтому итоговый score может отличаться от промежуточной оценки, которая видна во время выполнения аудита. В начале система знает только целевую страницу, а к финалу получает данные по конкурентам.

## 13. Формирование рекомендаций

Рекомендации строятся не как общий список советов. Система смотрит, где целевая страница отстаёт от конкурентов, насколько фактор важен для SEO и насколько его реально исправить.

Приоритет рекомендации зависит от:

- размера отставания от конкурентного ориентира;
- поисковой важности признака;
- управляемости изменения;
- принадлежности признака к техническому, текстовому, коммерческому или семантическому блоку.

Например, если у конкурентов чаще есть цены, условия доставки и контакты, а на целевой странице этих блоков нет, рекомендация будет связана не с абстрактным улучшением страницы, а с конкретным отсутствующим элементом.

## 14. Таймлайн

Таймлайн показывает, как выполнялся аудит. В нём можно увидеть:

- запуск аудита;
- загрузку страницы;
- постановку задач в очереди;
- обработку конкурентов;
- ошибки или предупреждения;
- финализацию результата.

Таймлайн полезен для демонстрации распределённых вычислений. Он показывает, что аудит состоит из отдельных стадий, а не выполняется как один скрытый серверный процесс.

## 15. Финальный результат

После завершения аудита пользователь получает:

- общий обзор результата;
- конкурентный score;
- оценку самой страницы;
- сравнение с конкурентами;
- список рекомендаций;
- сведения о качестве конкурентного контекста;
- таймлайн выполнения;
- отчёт для экспорта;
- запись в истории аудитов.

Такой результат помогает SEO-специалисту быстрее понять, почему страница уступает конкурентам по конкретному запросу и какие действия стоит выполнить в первую очередь.
